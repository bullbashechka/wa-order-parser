# PRD: приём заказов из WhatsApp Business и формирование документов развозки

## Цель продукта

Нужно разработать приложение, которое автоматически принимает корзины (заказы),
отправленные клиентами в WhatsApp Business, и превращает их в рабочие документы
склада и развозки:

1. **CSV-журнал заказов за день** — сырые строки заказов, сгруппированные по
   календарному дню получения.
2. **Экспедиционный лист (XLSX)** — сводный лист сборки: что и в каком суммарном
   количестве нужно собрать за день.
3. **Накладные на отпуск товара (XLSX)** — по одному бланку на каждого клиента за
   день, по шаблону `files/Заказ №1 от 12.06.2026.pdf`.

Сценарий использования: пока товар развозится по магазинам (например, 25 июня),
клиенты продолжают присылать заказы. Утром следующего дня (26 июня) система
автоматически закрывает предыдущий день — формирует экспедиционный лист и
накладные за 25 июня. По экспедиционному листу собирают товар, по накладным
развозят.

Приложение должно работать в фоне, сохранять авторизованную сессию WhatsApp, не
требовать повторного сканирования QR-кода после перезапуска и защищать данные от
повторной обработки одной и той же корзины.

## Технологии

Приложение разрабатывается на Node.js 18 или выше, в стиле CommonJS
(`require`/`module.exports`), с `'use strict'`.

- Подключение к WhatsApp — библиотека `whatsapp-web.js` (исходник лежит в корне
  этого же репозитория, см. раздел «Структура репозитория (монорепо)»).
- Отображение QR-кода в терминале — `qrcode-terminal`.
- CSV — `csv-writer` или эквивалент, корректно создающий файл, пишущий заголовки и
  добавляющий строки без потери существующих данных.
- XLSX (накладные и экспедиционные листы) — `exceljs` (чистый JS, без нативных
  зависимостей, корректная поддержка кириллицы и оформления ячеек).
- Конфигурация — `dotenv`.
- Планировщик ежедневной генерации — `node-cron` или эквивалент.
- Фоновый запуск — `pm2`.

## Структура репозитория (монорепо)

Репозиторий содержит **исходник библиотеки** `whatsapp-web.js` (корневые `index.js`,
`src/`, `tests/` и т.д.) и **приложение-продукт**. Приложение размещается в
отдельной папке и подключает библиотеку локально, не смешиваясь с её исходниками.

```
/                         # пакет библиотеки whatsapp-web.js (не трогаем)
  index.js                #   барель-экспорт библиотеки
  src/                    #   исходник библиотеки
app/                      # приложение wa-order-parser (продукт)
  package.json            #   свои зависимости; зависит от ../ (whatsapp-web.js: file:..)
  index.js                #   точка входа приложения (фоновый режим)
  lib/                    #   модули приложения
  cli/                    #   ручные команды (например, build-day)
  templates/              #   шаблоны XLSX/оформления, если нужны
  data/                   #   результаты работы (см. ниже)
  .env                    #   конфигурация приложения
  .env.example
```

Корневые npm-скрипты `start` и `build-day` делегируют в `app/`. Приложение зависит
от библиотеки как от локального пакета (`"whatsapp-web.js": "file:.."`).

## Архитектура приложения

Каждый модуль решает одну задачу:

- `config` — загрузка `.env` и значений по умолчанию.
- `clients` — справочник «телефон → имя клиента».
- `orderExtractor` — преобразование сообщения типа `ORDER` в нормализованные строки;
  здесь же из сообщения берётся `pushname`/имя контакта и кладётся в строку CSV.
- `dayStore` — запись CSV за день и защита от дублей (`processed-messages.json`).
- `expedition` — агрегация заказов дня в экспедиционный лист (XLSX).
- `invoice` — данные накладной по клиенту и рендер бланка (XLSX).
- `numberToWords` — сумма прописью (тенге/тиын, русский язык).
- `dayBuilder` — закрытие дня: вызывает `expedition` и `invoice` для всех клиентов дня.
- `scheduler` — ежедневный запуск `dayBuilder` за предыдущий день.
- `whatsapp` — настройка клиента (LocalAuth, подписка на события).
- `index` — сборка всего вместе (фоновый режим).
- `cli/build-day` — ручной запуск `dayBuilder` для указанной даты.

## Фича: авторизация в WhatsApp Business

Приложение подключается к WhatsApp через WhatsApp Web с помощью `LocalAuth`.

При первом запуске показывает QR-код в терминале; пользователь сканирует его в
WhatsApp на телефоне через раздел связанных устройств. После авторизации сессия
сохраняется в папку `.wwebjs_auth`. При последующих запусках сохранённая сессия
используется без повторного QR-кода, пока остаётся валидной.

В консоль выводятся только важные статусы: появление QR-кода, готовность клиента,
ошибки подключения.

## Фича: приём заказов из WhatsApp

Приложение слушает входящие сообщения и обрабатывает только сообщения типа
корзины/заказа, которые WhatsApp передаёт как `order` (`MessageTypes.ORDER`).

Текстовые сообщения, медиа, звонки, реакции и прочие события игнорируются и не
записываются. Приложение **не отправляет автоответы** — только принимает заказ.

Из заказа извлекается список товаров. Данные товара берутся по цепочке:
`Message` (тип `ORDER`) → `message.getOrder()` → `Order` (`.products`, `.currency`)
→ `Product` (`.name`, `.quantity`, `.price`, `.currency`).

Каждый товар корзины — это одна нормализованная строка с полями: дата и время,
телефон, ID сообщения, название товара, количество, цена, валюта, сумма позиции.
Если корзина содержит несколько товаров, у всех строк одинаковые дата, телефон и
ID сообщения. Отсутствующие у WhatsApp количество/цена/валюта оставляются пустыми;
сумма позиции считается только если есть и количество, и цена.

## Фича: группировка по дню получения

Заказ относится к тому **календарному дню**, когда корзина получена (по часовому
поясу из конфигурации, по умолчанию `Asia/Almaty`). Каждый день — свой набор
файлов.

Результаты складываются в папку дня:

```
app/data/days/YYYY-MM-DD/
  orders.csv          # сырые строки заказов за день (по строке на товар)
  expedition.xlsx     # экспедиционный лист (формируется при закрытии дня)
  invoices/           # накладные по клиентам (формируются при закрытии дня)
    Заказ №1 от DD.MM.YYYY — <Клиент>.xlsx
    ...
```

## Фича: CSV-журнал заказов за день

Сырые заказы за день пишутся в `orders.csv` внутри папки дня.

- Разделитель `;` (удобно открывается в Excel в русской/европейской локали).
- Если файла нет — он создаётся автоматически вместе со строкой заголовков.
- Заголовок:
  `Дата и время;Телефон;Имя клиента;ID сообщения;Название товара;Количество;Цена;Валюта;Сумма позиции`
- `Дата и время` — момент обработки в формате `YYYY-MM-DD HH:mm:ss`, в часовом поясе
  из конфигурации.
- `Телефон` — номер клиента без суффикса WhatsApp (`77001234567`, не
  `77001234567@c.us`).
- `Имя клиента` — имя контакта/`pushname` из WhatsApp на момент приёма заказа (см.
  «Фича: справочник клиентов»). Сохраняется **сырым**, как пришло из WhatsApp; если
  имени нет — пусто. Нужно, чтобы генерация документов на следующий день могла
  восстановить «Заказчика» из одного `orders.csv`, не подключаясь к WhatsApp.
- `ID сообщения` — уникальный ID входящего сообщения.
- `Название товара` — название из WhatsApp с обрезанными пробелами по краям; регистр
  не меняется.
- `Количество`, `Цена`, `Валюта` — заполняются, если переданы WhatsApp, иначе пусто.
- `Сумма позиции` — `Количество × Цена`, если оба значения есть, иначе пусто.

## Фича: защита от дублей

Уникальность корзины определяется по ID входящего сообщения WhatsApp.

Обработанные ID хранятся в файле `processed-messages.json` (общий для всех дней).
При запуске файл загружается. Корзина с уже известным ID повторно не записывается.
ID помечается обработанным **только после успешной записи всех строк** этой корзины
в `orders.csv` — чтобы при сбое корзину можно было обработать повторно.

## Фича: экспедиционный лист (XLSX)

При закрытии дня формируется `expedition.xlsx` — сводный лист сборки за день.

- Это лист для склада: что и сколько нужно собрать, без цен.
- Товары агрегируются по названию: одинаковые товары из разных заказов
  суммируются по количеству.
- Колонки: `№ | Товар | Кол-во | Ед. изм.`. У `whatsapp-web.js` `Product` нет поля
  единицы измерения, поэтому колонка `Ед. изм.` присутствует в листе, но **всегда
  пустая** (зарезервирована на будущее).
- В шапке: дата дня, заголовок «Экспедиционный лист», итоговое число позиций.
- Сортировка строк — по названию товара.

## Фича: накладные на отпуск товара (XLSX)

При закрытии дня формируется по одной накладной (XLSX) на каждого клиента, у
которого есть заказы за этот день. Накладная повторяет оформление шаблона
`files/Заказ №1 от 12.06.2026.pdf`:

- Заголовок: `Заказ клиента №N от DD месяца YYYY г.` (дата — словом по-русски, как в
  шаблоне).
- `Исполнитель:` — название организации из конфигурации (`COMPANY_NAME`).
- `Заказчик:` — имя клиента из справочника (см. ниже).
- Таблица: `№ | Товары | Кол-во | Цена | Сумма`. Одна строка на товар клиента за
  день; одинаковые товары клиента суммируются по количеству.
- `Итого:` — сумма по всем строкам.
- Строка «Всего наименований N, на сумму X KZT».
- Сумма прописью на русском языке (тенге/тиын), например
  «Семь тысяч тенге 00 тиын».
- Подпись: «Менеджер ____».

Правила:

- Накладная формируется **всегда** для каждого клиента дня, даже если у товаров нет
  цен. При отсутствии цены поля `Цена`, `Сумма`, `Итого` и сумма прописью остаются
  пустыми/нулевыми.
- Валюта — **всегда KZT (тенге)**, независимо от валюты, переданной WhatsApp.
- Нумерация `№N` **сбрасывается каждый день**: первый клиент дня — №1, второй — №2 и
  т.д. Порядок нумерации — по времени первого заказа клиента в этот день. При
  совпадении времени (точность CSV — секунда) ничья разрешается **по порядку строк в
  `orders.csv`** (сверху вниз): чья первая строка записана раньше, тот и раньше по
  номеру. Это делает нумерацию полностью детерминированной из файла дня.
- Имя файла: `Заказ №N от DD.MM.YYYY — <Клиент>.xlsx` (недопустимые для имени файла
  символы в имени клиента заменяются).

## Фича: справочник клиентов

Имя клиента берётся из справочника «телефон → имя» (файл по умолчанию
`clients.json`), сопоставление по очищенному номеру телефона.

Порядок определения имени (`Заказчик` в накладной и `<Клиент>` в имени файла)
применяется **на этапе генерации документов**:

1. Имя из справочника `clients.json` по номеру телефона (справочник — источник истины,
   читается на момент генерации, поэтому его можно обновлять задним числом).
2. Если номера нет в справочнике — значение колонки `Имя клиента` (`pushname`) из
   `orders.csv`, сохранённое при приёме заказа.
3. Если и его нет — сам номер телефона.

Поскольку приём заказов и генерация документов разнесены во времени (документы
формируются на следующий день, `build-day` читает только CSV), `pushname` фиксируется
в `orders.csv` в момент приёма (см. «Фича: CSV-журнал заказов за день»), а справочник
применяется поверх него при генерации.

Отсутствие справочника или номера в нём не должно прерывать работу.

## Фича: формирование документов по расписанию

Экспедиционный лист и накладные формируются **по расписанию**, а не в момент
прихода заказа.

- Каждый день в заданное время (`GENERATE_TIME`, по умолчанию `06:00` в часовом
  поясе из конфигурации) планировщик формирует документы за **предыдущий**
  календарный день.
- Если за предыдущий день нет ни одного заказа — документы не создаются, в консоль
  выводится сообщение.
- Повторный запуск генерации за уже обработанный день перезаписывает документы дня
  (нумерация и состав восстанавливаются детерминированно из `orders.csv` дня).

## Фича: ручная генерация за дату (CLI)

Должна быть команда ручного формирования документов за конкретную дату — на случай
пропущенного расписания или перегенерации:

```bash
npm run build-day -- 2026-06-25
```

Команда читает `orders.csv` указанного дня и формирует `expedition.xlsx` и
накладные так же, как это делает планировщик.

## Фича: обработка ошибок

- Запись в CSV при ошибке повторяется несколько раз. Если запись не удалась после
  повторов — ошибка логируется, приём следующих сообщений продолжается, ID **не**
  помечается обработанным.
- Ошибка формирования одной накладной логируется и не прерывает формирование
  остальных накладных и экспедиционного листа.
- Сбой планировщика за день не должен останавливать приём новых заказов; день можно
  перегенерировать вручную через `build-day`.
- Ошибка обработки одного заказа не останавливает приём следующих сообщений.

## Фича: конфигурация через `.env`

Настройки задаются через `.env` приложения. Поддерживаемые параметры и значения по
умолчанию:

```env
# приём и журнал
TIMEZONE=Asia/Almaty
CSV_DELIMITER=;
OUTPUT_DIR=app/data/days
PROCESSED_MESSAGES_PATH=app/data/processed-messages.json

# справочник клиентов
CLIENTS_PATH=app/clients.json

# генерация документов
GENERATE_TIME=06:00
COMPANY_NAME=Моя организация
INVOICE_CURRENCY=KZT
```

Если `.env` отсутствует или отдельные параметры не заданы — используются значения по
умолчанию. В репозитории должен быть `app/.env.example` с этими безопасными
значениями (текущий корневой `.env.example` относится к тестам библиотеки и не
трогается).

```bash

node app/index.js    # для разработки
```

Фоновый запуск через `pm2`:

```bash

```

Ручная генерация за дату:

```bash

```

## Фича: логирование

В консоль выводятся только важные события:

- QR-код / необходимость авторизации;
- готовность клиента;
- запись новой корзины (телефон, число товаров) и пропуск уже обработанной;
- формирование документов за день (день, число накладных, путь к папке);
- ошибки подключения, чтения конфигурации/справочника, чтения
  `processed-messages.json`, записи CSV и формирования XLSX.

Каждое входящее не-корзинное сообщение не логируется. Отдельный файл логов не нужен.

## Критерии приёмки

- Тестовая корзина, отправленная на WhatsApp Business, создаёт строки в
  `orders.csv` за текущий день; несколько товаров — несколько строк с одинаковыми
  датой, телефоном и ID сообщения.
- CSV содержит заголовок, разделитель `;`, дату в формате `YYYY-MM-DD HH:mm:ss` в
  часовом поясе `Asia/Almaty`, телефон без `@c.us`.
- Повторная обработка того же ID сообщения не создаёт дублей.
- После перезапуска используется сохранённая сессия без повторного QR-кода; через
  `pm2` приложение продолжает работать в фоне.
- В заданное время формируются `expedition.xlsx` (агрегат по товарам) и накладные
  по клиентам за предыдущий день.
- Экспедиционный лист суммирует одинаковые товары по количеству.
- На каждого клиента дня создаётся накладная XLSX по шаблону: нумерация
  сбрасывается каждый день, валюта KZT, сумма прописью на русском, «Заказчик» из
  справочника (с fallback на имя WhatsApp/телефон).
- `npm run build-day -- YYYY-MM-DD` формирует те же документы за указанную дату из
  её `orders.csv`.
- Ошибка одной накладной или одной записи не останавливает обработку остальных.

  «Структура репозитория (монорепо)». Текущий рабочий код в корне (`index.js`,
  `lib/`, `orders.csv`, `tests/` приложения) мигрирует в `app/` и подключает
  `whatsapp-web.js` как локальный пакет (`file:..`). Корневые `index.js`/`src/`
  библиотеки не трогаются.
- **Имя клиента для документов.** Имя контакта/`pushname` сохраняется в `orders.csv`
  отдельной колонкой `Имя клиента` в момент приёма заказа. Генерация документов
  восстанавливает «Заказчика» только из `orders.csv` + `clients.json`, без живого
  подключения к WhatsApp. Приоритет: `clients.json` → `Имя клиента` из CSV → номер.
- **Колонка «Ед. изм.» в экспедиционном листе.** Колонка остаётся в листе, но всегда
  пустая: у `whatsapp-web.js` `Product` нет поля единицы измерения.
- **Детерминизм нумерации накладных.** Порядок клиентов дня — по времени первого
  заказа; при равенстве секунды ничья разрешается по порядку строк в `orders.csv`
  (сверху вниз).

### Принятые умолчания (если не возразите)

- **Группировка в накладные — по телефону.** Одна накладная на каждый отдельный
  номер. Если два разных номера ведут на одно имя в `clients.json`, формируются две
  отдельные накладные.
- **Формат чисел в XLSX — как в шаблоне:** два знака после запятой, запятая в роли
  десятичного разделителя (например, `7 000,00`). В `orders.csv` цена по-прежнему
  пишется как есть, без переформатирования.
- **Поздние заказы.** Заказ, пришедший после `GENERATE_TIME` за уже «закрытый»
  предыдущий день, в автогенерацию не попадает; он добирается перезапуском
  `build-day` за нужную дату (перегенерация детерминированно перезаписывает документы
  дня).
